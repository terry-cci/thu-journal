# 同步互斥与死锁

## 关键知识点

### 锁、信号量、管程、条件变量、经典问题与银行家算法

---

# 本讲主线

## 五个核心问题

1. 为什么共享资源会导致并发错误？
2. 临界区、互斥、同步、原子操作分别是什么？
3. 锁、信号量、管程、条件变量如何设计和使用？
4. 如何求解生产者消费者、哲学家、读者写者问题？
5. 死锁如何产生、避免、检测和恢复？

---

# 为什么需要同步互斥？

独立进程/线程：

- 不共享资源或状态。
- 调度顺序通常不影响结果。
- 执行较容易重现。

共享资源的进程/线程：

- 调度顺序会影响结果。
- 可能产生数据竞争。
- 错误可能间歇性出现，难以调试。

同步互斥的目标：

> 在允许并发执行的同时，保证共享数据访问的正确性。

---

# 基本概念

| 概念 | 含义 |
|---|---|
| 原子操作 | 不可被中断地完整执行，要么成功，要么不执行 |
| 临界资源 | 多个执行流共享且需要互斥访问的资源 |
| 临界区 | 访问临界资源的一段代码 |
| 互斥 | 同一时刻最多一个执行流进入同一临界区 |
| 同步 | 控制多个执行流的先后关系 |

判断题：

| 说法 | 判断 |
|---|:---:|
| 临界区是访问共享资源的代码段，同一资源同一时刻最多一个执行流进入。 | <span class="ok">√</span> |

---

# 临界区结构

```text
entry section
  -> critical section
exit section
  -> remainder section
```

临界区访问规则：

1. 空闲则入：无人在临界区时，可以进入。
2. 忙则等待：有人在临界区时，其他执行流等待。
3. 有限等待：等待者不能无限期等待。
4. 让权等待：不能进入时最好释放 CPU，而不是一直忙等。

---

# 禁用中断

单核上：

- 关闭中断可防止当前 CPU 被中断打断。
- 可保护很短的内核临界区。

缺点：

- 不适合长临界区。
- 会影响系统响应。
- 用户程序不能随意关中断。
- 多核上只关本核中断挡不住其他 CPU。

判断题：

| 说法 | 判断 |
|---|:---:|
| 多核上仅靠关本核中断不能保证共享数据互斥，还需要 spinlock 等机制。 | <span class="ok">√</span> |

---

# 软件互斥算法

经典软件算法：

- Peterson 算法
- Dekker 算法
- Eisenberg-McGuire 算法

Peterson 算法思想：

- `flag[i]` 表示自己想进入。
- `turn` 表示谦让给谁。
- 适用于两个执行流的互斥。

重点：

> Peterson 不需要 test-and-set 指令，但依赖普通读写原子性和顺序一致的内存模型。

---

# 锁 Lock

锁是控制临界区访问的抽象。基本接口：

```text
lock.acquire()
critical section
lock.release()
```

实现方式：

- 禁用中断
- Test-and-Set
- Compare-and-Swap
- 自旋锁
- 阻塞锁 / 睡眠锁

关键问题：

- 是否忙等？- 是否公平？- 临界区多长？- 单核还是多核？

---

# 自旋锁 Spinlock

自旋锁：

- 拿不到锁时循环检查。
- 不睡眠，不让出 CPU。
- 适合多核、短临界区。

单核问题：

- 等锁者忙等占用 CPU。
- 持锁者可能得不到运行机会释放锁。
- 若持锁者被抢占，可能严重卡住。

多核上：

- 持锁者可能在另一个核运行并释放锁。
- 但长临界区会浪费大量 CPU。

---

# TAS / CAS

Test-and-Set：

```c
while (TestAndSet(&lock)) ;
critical_section();
lock = false;
```

Compare-and-Swap：

```c
bool cas(int *p, int old, int new) {
    if (*p == old) {
        *p = new;
        return true;
    }
    return false;
}
```

这些硬件原子指令是构造锁和无锁算法的重要基础。

# 信号量 Semaphore

信号量是一个受保护的整数和两个原子操作。

```text
P/down/wait:
  sem--
  if sem < 0: block current thread

V/up/signal:
  sem++
  if sem <= 0: wake one waiting thread
```

特点：

- P 可能阻塞。
- V 通常不阻塞。
- 等待队列由内核维护。
- PV 操作必须原子。

---

# 信号量用途

| 用途 | 初值 | 含义 |
|---|---:|---|
| 互斥锁 | 1 | 同一时刻只允许一个执行流进入临界区 |
| 条件同步 | 0 | 表达“某事件尚未发生，等待别人唤醒” |
| 资源计数 | N | 表示有 N 个可用同类资源 |

易错判断：

| 说法 | 判断 | 解释 |
|---|:---:|---|
| 用信号量实现互斥时初值应设为 0。 | <span class="bad">×</span> | 互斥初值通常为 1。 |
| 初值为 0 的信号量只能用于生产者消费者。 | <span class="bad">×</span> | 也可用于事件通知、线程汇合等。 |

---

# 信号量使用风险

PV 编程常见错误：

- 忘记 V，导致永久阻塞。
- 多 V，破坏互斥。
- P/V 顺序错误，造成死锁。
- 在持锁状态下阻塞不当。
- 不同资源申请顺序不一致，形成循环等待。

经验：

> 用信号量求解同步问题时，要先列出互斥约束和同步约束，再为每个约束设计信号量。

---

# 生产者消费者问题

约束：

- 任何时刻只能一个线程操作缓冲区。
- 缓冲区空时，消费者等待。
- 缓冲区满时，生产者等待。

信号量：

| 名称 | 初值 | 含义 |
|---|---:|---|
| `mutex` | 1 | 保护缓冲区互斥 |
| `empty` | N | 空槽数量 |
| `full` | 0 | 已有数据数量 |

---

# 生产者消费者模板

```c
void producer() {
    P(empty);
    P(mutex);
    put_item();
    V(mutex);
    V(full);
}

void consumer() {
    P(full);
    P(mutex);
    get_item();
    V(mutex);
    V(empty);
}
```

关键：

- 先等资源数量，再进入互斥区。
- 不要先拿 `mutex` 再等 `empty/full`，否则可能死锁。

---

# 管程 Monitor

管程是一种组织同步互斥的程序结构。

特点：

- 把共享数据和操作封装在一起。
- 外部只能通过管程过程访问共享数据。
- 任一时刻最多一个线程执行管程代码。
- 条件变量用于等待特定条件。

组成：

- 一个互斥锁
- 共享变量
- 若干条件变量
- 入口等待队列
- 条件等待队列

---

# 条件变量 Condition Variable

条件变量用于等待某个条件成立。

典型接口：

```c
pthread_mutex_lock(&lock);
while (!condition) {
    pthread_cond_wait(&cond, &lock);
}
use_shared_data();
pthread_mutex_unlock(&lock);
```

`wait` 的关键语义：

- 调用前必须持有互斥锁。
- 原子地释放互斥锁并进入等待队列。
- 被唤醒后重新获得互斥锁。
- 返回后应重新检查条件。

---

# 条件变量 vs 信号量

| 对比项 | 信号量 P/V | 条件变量 wait/signal |
|---|---|---|
| 是否保存资源数量 | 是，sem 计数 | 否，只表示等待队列 |
| 是否必须配合锁 | 不一定 | 通常必须配合互斥锁 |
| wait/P 行为 | P 消耗计数，可能阻塞 | wait 释放锁并睡眠 |
| signal/V 行为 | V 增加计数，可唤醒 | signal 唤醒等待者，不保存“信号” |

判断题：

| 说法 | 判断 |
|---|:---:|
| 条件变量 wait 和信号量 P 语义完全相同。 | <span class="bad">×</span> |

---

# 为什么 wait 后用 while？

`wait` 返回后条件不一定仍成立。

原因：

- 虚假唤醒。
- 被唤醒后重新竞争锁，条件可能被其他线程改变。
- `signal` 只说明“可能满足”，不是保证满足。

正确写法：

```c
while (!condition) {
    wait(cond, lock);
}
```

判断题：

| 说法 | 判断 |
|---|:---:|
| 使用条件变量时，从 wait 返回后通常应在循环中重新检查条件。 | <span class="ok">√</span> |

---

# Hoare / Mesa / Hansen 管程

| 类型 | signal 后谁运行 |
|---|---|
| Hoare | 被唤醒线程立即运行，signal 者等待 |
| Mesa | signal 者继续运行，被唤醒线程重新竞争锁 |
| Hansen | signal 通常作为离开管程前的最后操作 |

现代 pthread / Java 更接近 Mesa 语义。

所以：

> 被唤醒不等于条件必然成立，必须重新检查条件。

# 哲学家就餐问题

死锁风险：

- 每个哲学家先拿左叉。- 再等待右叉。
- 所有人都持有一个资源并等待另一个资源。
- 形成循环等待。
解决思路：
- 限制最多 4 个哲学家同时尝试拿叉子。
- 规定资源申请顺序。
- 一次性申请两把叉子，拿不到就都不拿。
- 使用管程记录状态，只在左右邻居都未进餐时允许进餐。

判断题：

| 说法 | 判断 |
|---|:---:|
| 限制最多 4 个哲学家同时尝试拿叉子能避免死锁。 | <span class="ok">√</span> |

---

# 读者写者问题

约束：

- 读-读：允许并发。
- 读-写：互斥。
- 写-写：互斥。

策略：

| 策略 | 特点 | 风险 |
|---|---|---|
| 读者优先 | 有读者时新读者可进入 | 写者饥饿 |
| 写者优先 | 有写者等待时阻止新读者 | 读者可能饥饿 |
| 公平策略 | 按队列顺序 | 实现复杂 |

---

# 读者优先代码机制

```c
semaphore rw_mutex = 1;
semaphore read_cnt_mutex = 1;
int read_count = 0;
```

机制：

- 第一个读者 `down(rw_mutex)`，阻止写者。
- 后续读者只增加 `read_count`，可并发读。
- 最后一个读者 `up(rw_mutex)`，释放写者。
- `read_cnt_mutex` 保护 `read_count`。

风险：

> 读者源源不断到达时，写者可能长期等待。

---

# 写者优先思想

增加：

```c
semaphore write_cnt_mutex = 1;
semaphore queue_mutex = 1;
int write_count = 0;
```

核心：

- 第一个写者到来时获取 `queue_mutex`。
- 新读者被挡在入口。
- 已经进入的读者读完后释放 `rw_mutex`。
- 写者获得写权限。
- 最后一个写者离开时释放读者入口。

---

# 死锁是什么？

死锁：

> 两个或更多进程/线程由于竞争资源或通信关系，永远相互等待只能由对方触发的事件。

例子：

```c
Thread 1:       Thread 2:
lock(L1);       lock(L2);
lock(L2);       lock(L1);
```

结果：

- T1 持有 L1，等 L2。
- T2 持有 L2，等 L1。
- 双方都无法继续。

---

# 死锁四个必要条件

| 条件 | 含义 |
|---|---|
| 互斥 | 资源不能同时被多个执行流使用 |
| 持有并等待 | 已持有资源的同时继续等待其他资源 |
| 不可抢占 | 资源不能被强行夺走，只能自愿释放 |
| 循环等待 | 等待关系形成环 |

判断题：

| 说法 | 判断 |
|---|:---:|
| 死锁产生通常需要四个必要条件同时成立。 | <span class="ok">√</span> |

---

# 资源分配图

资源分配图：

- 进程节点：`P_i`
- 资源节点：`R_j`
- 请求边：`P_i -> R_j`
- 分配边：`R_j -> P_i`

结论：

| 资源实例数 | 图中有环意味着 |
|---|---|
| 每类资源只有一个实例 | 有环通常表示死锁 |
| 每类资源有多个实例 | 有环不一定死锁 |

判断题：

| 说法 | 判断 |
|---|:---:|
| 资源分配图有环就一定死锁，即使每类资源有多个实例。 | <span class="bad">×</span> |

---

# 死锁处理方法

| 方法 | 思路 |
|---|---|
| 死锁预防 | 破坏四个必要条件之一 |
| 死锁避免 | 分配前判断是否仍安全 |
| 死锁检测 | 允许死锁发生，周期性检测 |
| 死锁恢复 | 检测后终止进程、抢占资源或回滚 |
| 忽略 | 许多通用 OS 对部分应用死锁不主动处理 |

---

# 死锁预防

破坏条件：

| 条件 | 破坏方式 | 代价 |
|---|---|---|
| 互斥 | 尽量共享化资源 | 很多资源无法共享 |
| 持有并等待 | 一次性申请所有资源 | 资源利用率低 |
| 不可抢占 | 允许抢占或回滚 | 实现复杂 |
| 循环等待 | 资源编号，按序申请 | 编程限制大 |

经典策略：

> 统一资源申请顺序可避免循环等待。

---

# 死锁避免

死锁避免在资源分配前检查：

> 如果这次分配后系统仍处于安全状态，才允许分配。

安全状态：

- 存在一个安全序列。
- 按这个序列，所有进程最终都能得到所需资源、完成并释放资源。

重要区别：

| 状态 | 含义 |
|---|---|
| 安全状态 | 一定没有死锁 |
| 不安全状态 | 不一定已经死锁，但可能演化为死锁 |

---

# 银行家算法

数据结构：

| 名称 | 含义 |
|---|---|
| Available | 当前可用资源向量 |
| Max | 每个进程最大需求 |
| Allocation | 每个进程已分配资源 |
| Need | 还需要的资源，`Need = Max - Allocation` |

分配请求时：

1. 检查 `Request <= Need`。
2. 检查 `Request <= Available`。
3. 试分配。
4. 判断试分配后是否仍安全。
5. 安全则批准，否则等待。

---

# 银行家算法例题

资源总数：

$$
(A,B,C)=(12,6,8)
$$

已分配总和：

$$
(9,5,5)
$$

所以：

$$
Available=(12,6,8)-(9,5,5)=(3,1,3)
$$

Need：

| 进程 | Need |
|---|---|
| P0 | (3,1,1) |
| P1 | (1,2,3) |
| P2 | (4,1,2) |
| P3 | (2,2,2) |
| P4 | (1,1,1) |

---

# 银行家算法安全序列

初始 `Work=(3,1,3)`。

| 步骤 | 进程 | Work 变化 |
|---:|---|---|
| 1 | P0 | (3,1,3) -> (4,3,5) |
| 2 | P4 | (4,3,5) -> (6,4,6) |
| 3 | P3 | (6,4,6) -> (6,6,7) |
| 4 | P1 | (6,6,7) -> (8,6,8) |
| 5 | P2 | (8,6,8) -> (12,6,8) |

系统安全。

安全序列：

`P0 -> P4 -> P3 -> P1 -> P2`

---

# 银行家算法请求判断

P1 请求：

$$
Request_1=(1,2,1)
$$

检查：

$$
Request_1 \le Need_1=(1,2,3) \quad \checkmark
$$

$$
Request_1 \le Available=(3,1,3) \quad \times
$$

B 分量 `2 > 1`，不能直接满足。

若让 P1 等待，不会死锁，因为 P0、P4 仍可完成并释放资源。

# 死锁检测与恢复

死锁检测：

- 允许系统进入死锁。
- 维护资源分配信息或等待图。
- 周期性检测是否有死锁。

恢复方法：

- 终止所有死锁进程。
- 一次终止一个进程，直到解除死锁。
- 抢占资源并回滚。

恢复选择因素：

- 进程优先级
- 已运行时间
- 持有资源量
- 还需资源量
- 交互/批处理性质

---

# 同步机制与进程/线程关系

同步互斥机制影响进程/线程状态：

```text
P/down/wait 失败
  -> 当前线程/进程阻塞
  -> 加入等待队列
  -> 调度器切换任务

V/up/signal/unlock
  -> 唤醒等待队列中的线程/进程
  -> 进入就绪态
```

内核数据结构常包含：

- 锁状态
- 等待队列
- 持有者信息
- 被阻塞的任务列表

---

# 与 IPC / 文件系统 / 虚拟内存的关系

| 场景 | 需要同步互斥的原因 |
|---|---|
| 管道 | 管道缓冲区读写、空/满等待队列 |
| 共享内存 | 多进程直接访问同一物理页 |
| 文件系统 | inode、块缓存、目录项、文件偏移 |
| 虚拟内存 | 页表修改、物理页帧分配、COW 引用计数 |
| 多线程进程 | 线程共享堆、全局变量和打开文件表 |

结论：

> 同步互斥机制是 OS 各个子系统共享状态正确性的基础。

# 高频判断题汇总

| 说法 | 判断 | 解释 |
|---|:---:|---|
| 信号量初值为 1 时可用于互斥，初值为 0 也可用于事件同步。 | <span class="ok">√</span> | 初值 0 不只用于生产者消费者。 |
| 多核上只关本核中断就能保护全局共享数据。 | <span class="bad">×</span> | 其他 CPU 仍可能进入临界区。 |
| 不安全状态说明系统已经死锁。 | <span class="bad">×</span> | 只是可能演化为死锁。 |
| Peterson 算法不需要硬件 TAS，但依赖读写原子性和内存顺序。 | <span class="ok">√</span> | 软件互斥算法的前提。 |

# 高频判断题汇总

| 说法 | 判断 | 解释 |
|---|:---:|---|
| 条件变量 wait 和信号量 P 完全相同。 | <span class="bad">×</span> | wait 释放锁并等待条件。 |
| 读者优先可能导致写者饥饿。 | <span class="ok">√</span> | 读者持续到达时写者长期等待。 |
| 自旋锁适合保护很长的临界区。 | <span class="bad">×</span> | 长临界区忙等浪费 CPU。 |
| 银行家算法属于死锁避免。 | <span class="ok">√</span> | 分配前检查安全状态。 |

# 解题策略

同步题：

1. 找共享资源。
2. 找互斥关系。
3. 找先后同步关系。
4. 设计锁/信号量/条件变量。
5. 检查是否可能死锁或饥饿。

死锁题：

1. 判断四个必要条件。
2. 看资源分配图是否有环。
3. 单实例资源：有环通常死锁。
4. 多实例资源：用银行家或检测算法判断。
5. 区分“不安全”和“已死锁”。

# 总结

- 临界区是访问共享资源的代码段。
- 锁适合互斥，信号量可用于互斥和同步。
- 条件变量必须配合互斥锁，wait 后通常用 while 重查条件。
- 管程把共享数据、锁和条件变量封装起来。
- 生产者消费者考互斥 + 空/满同步。
- 读者写者考读读共享、读写互斥、饥饿策略。
- 死锁四条件：互斥、持有并等待、不可抢占、循环等待。
- 银行家算法通过安全状态检查避免死锁。
