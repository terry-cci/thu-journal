# 习题讲解-2026.06.01
## 实时调度算法
### 对错判断
- RM（Rate Monotonic）实时调度算法采用静态优先级，周期越短的周期任务优先级越高。
- EDF（Earliest Deadline First）算法在整个系统运行期间为每个任务固定一个不变的优先级。

---
# 实时调度算法

| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
| - | <span class="ok">√</span> | RM 采用静态优先级，周期越短优先级越高 | RM，即 Rate Monotonic，是经典**静态优先级**实时调度算法，任务优先级由周期决定。 |
| - | <span class="bad">×</span> | EDF 为每个任务固定优先级 | EDF，即 Earliest Deadline First，是**动态优先级**算法，谁的绝对截止时间最早，谁优先级最高。 |

# 实时调度算法

## RM、EDF 与 LLF 的关键区别

| 对比项        | RM             | EDF                     | LLF                          |
| ---------- | -------------- | ----------------------- | ---------------------------- |
| 全称         | Rate Monotonic | Earliest Deadline First | Least Laxity First           |
| 中文名称       | 速率单调调度         | 最早截止时间优先                | 最低松弛度优先                      |
| 优先级类型      | 静态优先级          | 动态优先级                   | 动态优先级                        |
| 优先级是否随运行变化 | 不变             | 会变化                     | 会频繁变化                        |
| 优先级依据      | 任务周期长短         | 任务的绝对截止时间               | 任务的松弛度                       |
| 核心规则       | 周期越短，优先级越高     | 截止时间越早，优先级越高            | 松弛度越小，优先级越高                  |
| 关注重点       | 任务释放频率         | 任务 deadline 的远近         | 任务是否还有“空闲余量”                 |


RM 看“周期”，EDF 看“最近的 deadline”。LLF看“松弛度”：表示这个任务还可以“最多拖多久”而不影响按时完成。


$$
松弛度：L = DeadLine - CurrTime - C_{task\_remaining\_time}
$$

# 实时调度算法

## RM、EDF 与 LLF 的关键区别

| 对比项        | RM             | EDF                     | LLF                          |
| ---------- | -------------- | ----------------------- | ---------------------------- |
| 是否考虑剩余执行时间 | 不直接考虑          | 不直接考虑                   | 直接考虑                         |
| 是否适合周期任务   | 非常适合周期任务       | 适合周期任务和非周期任务            | 理论上适合实时任务，但实现成本较高            |
| 调度开销       | 较低             | 中等                      | 较高                           |
| 抢占频率       | 较低             | 中等                      | 可能很高                         |
| 实现复杂度      | 较简单            | 较复杂                     | 最复杂                          |
| 理论性质       | 固定优先级算法中经典方法   | 单处理器可抢占实时调度中具有很强的最优性    | 理论上很灵活，但容易导致频繁调度             |
| 典型优点       | 简单、稳定、易实现      | CPU 利用率高，调度能力强          | 能更精确反映任务紧急程度                 |
| 典型缺点       | CPU 利用率上界相对保守  | 需要动态维护 deadline 顺序      | 调度抖动和上下文切换开销大                |
| 常见误区       | 把周期和截止时间混淆     | 误认为 EDF 的优先级固定          | 误认为 LLF 只看 deadline，不看剩余执行时间 |

# 多处理器与线程
## 对错判断
- 在多处理器系统中，仅在本 CPU 上关闭中断，不能保证其他 CPU 不会同时进入同一临界区。
- 同一进程内的多个线程通常共享地址空间和打开文件表，但每个线程仍需要各自的执行上下文。

---
# 多处理器与线程

| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
| - | <span class="ok">√</span> | 多核中只关本 CPU 中断不能保证全局互斥 | 关闭本 CPU 中断只能防止本 CPU 被中断打断，不能阻止其他 CPU 同时进入临界区。多核互斥需要锁或原子操作。 |
| - | <span class="ok">√</span> | 同一进程内线程共享资源，但各有执行上下文 | 线程共享地址空间、打开文件等资源，但每个线程有自己的程序计数器、寄存器、栈等上下文。 |

---
# 多处理器与线程
## 多核临界区：为什么“关中断”不够？


单处理器中：

> 关闭中断可以防止当前执行流被中断处理程序或调度打断。

多处理器中：

> 其他 CPU 仍然可以并发执行同一段内核代码。

因此，多核环境下保护共享数据通常需要：

- 自旋锁 - 互斥锁 - 读写锁
- 原子指令
- 禁用抢占 + 锁组合机制

# 管道与文件描述符
## 对错判断
- 管道（pipe）的读操作只会复制数据而不会消耗数据，因此多个读者可以反复读到同一批已写入字节。
- 文件描述符表把用户态看到的整数 fd 与内核中的打开文件对象关联起来。
- `dup` 或 `fork` 后，若多个 fd 指向同一个打开文件对象，关闭其中任意一个 fd 都会立即释放底层文件对象。

---
# 管道与文件描述符

| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
| - | <span class="bad">×</span> | pipe 读操作只复制不消耗 | 管道是字节流，读操作会**消耗**数据。多个读者竞争读取，不能反复读同一批字节。 |
| - | <span class="ok">√</span> | fd 表关联整数 fd 与打开文件对象 | 用户态看到的是整数 fd，内核通过文件描述符表找到对应的打开文件对象。 |
| - | <span class="bad">×</span> | 关闭任一 fd 会立即释放底层对象 | `dup` 或 `fork` 后，多个 fd 可能指向同一个打开文件对象。关闭一个 fd 只减少引用计数，最后一个关闭才释放对象。 |

---
# 管道与文件描述符

## fd、打开文件对象、inode 的关系

```text
进程文件描述符表
  fd 3 ─┐
        ├──> 打开文件对象：offset、flags、引用计数
  fd 4 ─┘             │
                      v
                 inode / vnode
                      │
                      v
                   文件数据块
```

重点：

- `fd` 是进程看到的整数句柄。
- 打开文件对象保存文件偏移量、打开标志、引用计数等。
- inode 保存文件元数据和数据块位置。

# 目录、inode 与块缓存
## 对错判断
- 目录可以看作一种特殊文件，其内容描述“文件名到文件元数据位置”的映射关系。
- 在基于 inode 的文件系统中，文件名通常保存在 inode 自身内部，而不是保存在目录项中。
- 块缓存可以减少重复访问块设备的开销，也有助于把文件系统对块的读写集中管理。

---
# 目录、inode 与块缓存

| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
|- | <span class="ok">√</span> | 目录是特殊文件，描述文件名到元数据位置的映射 | 目录内容通常是目录项，保存“文件名 → inode 号”等映射关系。 |
| - | <span class="bad">×</span> | 文件名通常保存在 inode 内部 | 文件名通常保存在**目录项**中，inode 主要保存权限、大小、时间戳、数据块指针等元数据。 |
| - | <span class="ok">√</span> | 块缓存减少重复访问块设备的开销 | 块缓存能减少重复磁盘 I/O，并帮助文件系统集中管理块读写。 |

# 目录、inode 与块缓存

## inode 文件系统中的名字与元数据

```text
目录项 directory entry
  "a.txt" ───────────────> inode #128

  权限
  所有者
```

**文件名不属于 inode 本身。**

同一个 inode 可以通过多个目录项被引用，这也是硬链接的基础。

# 用户缓冲区与系统调用
## 为什么内核不能直接“相信”用户指针？

用户传入的缓冲区地址可能：

- 没有映射到有效物理页
- 没有对应读写权限
- 横跨多个页
- 在拷贝过程中触发缺页
- 指向非法或恶意地址

因此 `read` / `write` 需要专门的安全拷贝逻辑，例如 `copy_to_user` / `copy_from_user` 一类机制。

# 信号量、条件变量与管程
## 对错判断
- 信号量初值为 1 时可用于互斥；初值为 0 时也可用于表达两个执行流之间的先后同步。
- 条件变量的 `wait` 操作通常需要与互斥锁配合，等待前释放锁，被唤醒后再重新获得锁。
- 管程通过条件变量队列保证等待者最终会被唤醒，因此进入管程时不需要互斥锁保护共享数据。

---

# 信号量、条件变量与管程

| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
| - | <span class="ok">√</span> | 信号量初值为 1 可互斥，初值为 0 可同步 | 初值为 1 时类似互斥锁；初值为 0 时可表达“先完成者唤醒后等待者”。 |
| - | <span class="ok">√</span> | 条件变量 `wait` 要与互斥锁配合 | `wait` 通常会原子释放锁并睡眠，被唤醒后重新获得锁。 |
| - | <span class="bad">×</span> | 管程不需要互斥锁保护共享数据 | 管程强调对共享数据的互斥访问，条件变量不能替代互斥保护。 |

---
# 信号量、条件变量与管程
## 条件变量的一般使用模式

```c
pthread_mutex_lock(&lock);

while (!condition) {
    pthread_cond_wait(&cond, &lock);
}

use_shared_data();

pthread_mutex_unlock(&lock);
```

重点：

- `wait` 前必须持有锁； `wait` 会释放锁并睡眠。
- 被唤醒后重新获得锁。
- 条件检查通常使用 `while`，不是 `if`。

# 死锁
## 对错判断
- 死锁产生的必要条件包括互斥、持有并等待、不可抢占和循环等待。
- 若资源分配图中存在环路，且每类资源都只有一个实例，则系统必然处于死锁状态。
- 银行家算法的核心目标是在资源分配前判断系统是否仍可保持安全状态，从而避免进入不安全状态。

# 死锁
## 死锁条件与处理思路

| 必要条件 | 含义 | 常见破坏方式 |
|---|---|---|
| 互斥 | 资源不能同时共享 | 尽量共享化资源 |
| 持有并等待 | 拿着资源还继续等资源 | 一次性申请资源 |
| 不可抢占 | 资源不能被强制夺走 | 允许抢占或回滚 |
| 循环等待 | 形成等待环 | 资源有序分配 |

银行家算法属于**死锁避免**策略。

# 死锁
**每类资源只有一个实例时，资源分配图中存在环路是死锁的充分必要条件。** 
| 必要条件 | 含义 | 常见破坏方式 |
|---|---|---|
| 互斥 | 资源不能同时共享 | 尽量共享化资源 |
| 持有并等待 | 拿着资源还继续等资源 | 一次性申请资源 |
| 不可抢占 | 资源不能被强制夺走 | 允许抢占或回滚 |
| 循环等待 | 形成等待环 | 资源有序分配 |

这句话正确，因为它有一个重要的隐含前提：**当每类资源只有一个实例**，并且其他三个死锁必要条件（互斥、持有并等待、不可抢占）默认已满足时，资源分配图中存在环路，就是死锁的充分必要条件：资源分配图有环⟺存在死锁

---
# 死锁
## 为什么多实例资源时不一定？
关键区别在于：
- 一类资源如果有多个实例，即使其中一个实例被占用，其他实例也可能还能满足等待进程。

例如资源 𝑅1 有两个实例。图中可能出现：
```
P1 → R1 → P2
```
这表示 𝑃1请求 𝑅1，而 𝑅1的某个实例分配给了 𝑃2。但如果 𝑅1 还有另一个空闲实例，那么 𝑃1 仍然可能获得 𝑅1，不一定必须等 𝑃2
所以多实例情况下，即使图中有环，也不一定死锁。

# 设备管理
## 对错判断
- DMA 方式下，设备控制器可以直接在设备和内存之间搬运数据，但 CPU 仍需要参与初始化和完成处理。
- 中断方式一定比轮询方式更适合所有设备访问场景，因此现代操作系统不再需要轮询。
- 将设备抽象为文件接口后，`read` / `write` 的统一调用路径可以屏蔽部分设备差异，但驱动内部仍需处理具体设备协议。

---
# 设备管理
| 题号 | 判断 | 说法要点 | 解释 |
|---:|:---:|---|---|
| - | <span class="ok">√</span> | DMA 可直接在设备和内存间搬运数据 | CPU 不逐字节搬运，但仍要初始化 DMA、设置缓冲区、启动传输并处理完成事件。 |
| - | <span class="bad">×</span> | 中断一定比轮询更适合所有场景 | 高频事件、短等待、批量网络收包等场景中，轮询或混合方式可能更高效。 |
| - | <span class="ok">√</span> | 设备文件接口屏蔽部分差异，但驱动仍处理协议 | `read` / `write` 提供统一接口，具体寄存器、DMA、中断、协议仍由驱动处理。 |

---
# 设备管理
## 中断 vs 轮询

| 方式 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| 中断 | CPU 不必一直等待 | 高频中断开销大 | 低频、不可预测事件 |
| 轮询 | 控制简单，批处理效率高 | 可能浪费 CPU | 高频、短等待、网络收包 |
| 混合 | 兼顾响应与吞吐 | 实现更复杂 | 现代高性能 I/O |

结论：  
- **现代操作系统并没有放弃轮询。**
- **DMA 搬数据，CPU 管开始和收尾。**

# 选择题

 某设备需要进行大块数据传输，目标是减少 CPU 逐字节搬运数据的开销。操作系统更适合优先采用：

   A. 反复轮询设备状态并由 CPU 搬运全部数据
   B. 通过 DMA 让设备控制器和内存之间直接传输数据
   C. 把设备数据先写入目录项，再由用户程序读取目录项
   D. 禁止所有中断直到传输完成

---   
## 答案：<span class="answer">B</span>

DMA，即 Direct Memory Access，允许设备控制器直接在设备和内存之间搬运数据。

它的作用是：

- 避免 CPU 逐字节复制大量数据
- 降低 CPU 占用
- 适合磁盘、网卡、声卡等大块或高速 I/O 设备

CPU 仍然需要负责：

- 设置 DMA 控制器
- 指定内存缓冲区
- 启动传输
- 处理中断或完成通知

---

#  其他选项为什么不对？

| 选项 | 判断 | 原因 |
|---|---|---|
| A | 错 | CPU 轮询并搬运全部数据，正好没有减少 CPU 开销。 |
| C | 错 | 目录项保存文件名到 inode 的映射，不用于保存设备传输数据。 |
| D | 错 | 长时间禁止所有中断会严重影响系统响应性，也不能解决数据搬运开销问题。 |

# 选择题

某进程执行 `read(fd, buf, len)` 读取普通文件。内核通过 fd 找到打开文件对象后，下一步最合理的是：

A. 根据文件对象中的 inode 和当前偏移定位要读的文件数据块  
B. 直接把 fd 当作磁盘块号读取块设备  
C. 跳过文件系统结构，直接顺序扫描整个磁盘  
D. 先关闭该 fd，再重新分配一个新的 fd

---
## 答案：<span class="answer">A</span>

普通文件读取的大致路径是：

```text
用户 fd
  ↓
进程文件描述符表
  ↓
打开文件对象
  ↓
inode
  ↓
文件数据块
  ↓
拷贝到用户缓冲区 buf
```

打开文件对象通常保存：

- 当前文件偏移量、访问模式和标志、指向 inode 的引用

因此通过 inode 和当前偏移定位数据块，是最合理的下一步。

---

# 其他选项为什么不对？
某进程执行 `read(fd, buf, len)` 读取普通文件。内核通过 fd 找到打开文件对象后，下一步最合理的是：

A. 根据文件对象中的 inode 和当前偏移定位要读的文件数据块  
B. 直接把 fd 当作磁盘块号读取块设备  
C. 跳过文件系统结构，直接顺序扫描整个磁盘  
D. 先关闭该 fd，再重新分配一个新的 fd

| 选项 | 判断 | 原因 |
|---|---|---|
| B | 错 | fd 是用户态整数句柄，不是磁盘块号。 |
| C | 错 | 文件系统不会为了一次普通文件读取而顺序扫描整个磁盘。 |

```text
                          ├─ data block address
```

某文件系统采用 inode 保存文件的数据块索引。一个 inode 中包含：

- 1 个一级间接地址项；

每个地址项大小为 4 字节，数据块和索引块大小均为 1 KiB。

1. 计算一个一级间接索引块最多能保存多少个数据块地址。
2. 计算该 inode 能表示的单个文件最大大小，要求写出计算过程。

---
1. 一个一级间接索引块可保存的地址数：
   `1 KiB / 4 B = 1024 / 4 = 256` 个地址。

2. 最大文件大小：
   - 直接索引可表示 `4` 个数据块。
   - 一级间接可表示 `256` 个数据块。

1. fd 重定向关系：

   - 每个进程只保留自己需要的端，避免资源泄漏，也避免错误地让读端或写端一直保持打开。
