# 文件系统

## 关键知识点

### 设计与实现、日志文件系统、与虚拟内存 / 进程的关系

---

# 本讲主线

## 五个核心问题

1. 文件系统给用户和内核分别提供什么视图？
2. fd、打开文件对象、inode、目录项之间是什么关系？
3. 文件数据块如何分配和寻址？
4. 块缓存、页缓存、日志如何影响性能与一致性？
5. 文件系统如何与进程、虚拟内存和系统调用协同？

---

# 文件系统是什么？

文件系统是存储设备上组织文件的方法和数据结构，也是 OS 中负责文件命名、存储和检索的子系统。

用户视图：

- 文件是有名字的字节序列。
- 通过 `open/read/write/close` 等系统调用访问。
- UNIX 类系统强调“一切皆文件”。

内核视图：

- 文件是数据块和元数据的集合。
- 需要管理 inode、目录项、位图、缓存、设备 I/O。

---

# 文件系统的分层

```text
应用程序
  -> 系统调用 open/read/write/close
  -> VFS 统一接口
  -> 具体文件系统 ext/easy-fs/FAT/...
  -> 块缓存 / 页缓存
  -> 块设备驱动
  -> 磁盘 / SSD / virtio
```

关键点：

- VFS 屏蔽具体文件系统差异。
- 具体文件系统负责磁盘布局和元数据解释。
- 设备驱动负责真正的块读写。

---

# VFS 的作用

VFS：Virtual File System。

| 功能 | 说明 |
|---|---|
| 统一接口 | 不同文件系统都提供统一的文件操作接口 |
| 管理对象 | 管理 vnode/inode、目录项、打开文件对象等 |
| 路径查找 | 支持从路径名查找到具体文件对象 |
| 多 FS 共存 | 让磁盘 FS、内存 FS、设备文件等统一访问 |

重点：

> 应用看到的是 `read(fd, buf, len)`，内核会通过 fd 和 VFS 分派到具体文件对象的读操作。

---

# 文件系统基本数据结构

| 数据结构 | 作用 |
|---|---|
| superblock | 文件系统整体信息：块大小、inode 数、空闲块数等 |
| inode / vnode | 文件元数据：大小、权限、所有者、时间、数据块位置 |
| directory entry | 目录项：文件名到 inode 号的映射 |
| data block | 文件或目录的实际数据 |
| bitmap | 记录 inode / 数据块是否空闲 |
| block cache | 缓存磁盘块，减少设备 I/O |

---

# inode 与目录项

inode 保存：

- 文件类型；权限
- 所有者和组；文件大小
- 时间戳；链接数
- 数据块位置：直接、间接、多级间接指针

目录项保存：

- 文件名
- 对应 inode 号

关键结论：

> 文件名通常不在 inode 里，而在目录项里。

---

# inode、目录项、数据块

```text
目录 data block
  "a.txt" -> inode #128
  "b.txt" -> inode #256

inode #128
  size, mode, owner, link count
  direct blocks
  indirect blocks
       |
       v
  data blocks
```

重命名文件通常修改目录项，不是修改 inode 中的文件名。

硬链接的基础：

- 多个目录项可以指向同一个 inode。
- inode 链接计数记录有多少目录项引用它。

---

# fd、打开文件对象、inode

```text
进程文件描述符表
  fd 3 ─────> 打开文件对象
               offset
               flags
               refcnt
               inode pointer
                    |
                    v
                 inode
                    |
                    v
              data blocks
```

关键点：

- fd 是进程看到的整数索引。
- 打开文件对象保存偏移量和打开标志。
- inode 保存文件元数据和数据块位置。

---

# open、dup、fork 的共享关系

| 操作 | 结果 |
|---|---|
| 分别 `open` 同一文件 | 通常得到不同打开文件对象，文件偏移独立 |
| `dup` | 新 fd 指向同一个打开文件对象，共享 offset |
| `fork` | 子进程继承 fd 表，父子 fd 指向同一打开文件对象 |
| `close` | 关闭一个 fd 只减少引用计数，最后一个引用关闭才释放对象 |

重点：

> “两个进程分别 open 同一文件后偏移量独立”通常为真；“fork 后 fd 指向同一打开文件对象”也通常为真。

---

# 文件描述符不是文件数据

判断题：

| 说法 | 判断 | 解释 |
|---|:---:|---|
| 文件描述符表项直接保存文件在磁盘上的所有数据块号，因此 read 不需要经过 file 对象或 inode。 | <span class="bad">×</span> | fd 是索引；read 要通过 file 对象，再经 inode 定位数据块。 |

`read(fd, buf, len)` 的下一步不是把 fd 当块号。

正确路径：

```text
fd -> file object -> inode -> block mapping -> block cache -> device
```

---

# 目录文件

目录可以看作特殊文件。

目录内容是目录项集合：

```text
文件名 -> inode 号
```

目录操作：

- 创建文件：分配 inode，写入目录项。
- 删除文件：移除目录项，减少链接计数。
- 重命名：修改目录项。
- 路径查找：逐级查目录项。

重点：

> 目录的核心作用之一是维护“文件名到 inode 号”的映射关系。

---

# unlink 与文件回收

`unlink` 的语义：

- 从目录中删除一个名字。
- inode 链接计数减 1。
- 如果链接计数变为 0 且没有打开引用，才回收 inode 和数据块。

如果文件仍被进程打开：

- 目录项消失。
- 进程仍可通过已打开 file 对象访问文件内容。
- 最后一个打开引用关闭后，文件内容才释放。

---

# 硬链接与软链接

| 类型 | 本质 | 是否跨文件系统 | 目标删除后 |
|---|---|---|---|
| 硬链接 | 新目录项指向同一 inode | 通常不能 | 只要链接计数 > 0，文件仍存在 |
| 软链接 | 一个保存路径名的特殊文件 | 可以 | 软链接仍存在，但变成悬空链接 |

判断题：

| 说法 | 判断 |
|---|:---:|
| 硬链接和软链接都可以跨文件系统。 | <span class="bad">×</span> |
| 软链接目标删除后，软链接本身自动删除。 | <span class="bad">×</span> |

---

# 文件数据块分配方式

| 分配方式 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| 连续分配 | 文件占用连续块 | 顺序和随机访问快 | 外部碎片，扩展困难 |
| 链式分配 | 数据块组成链表 | 增删容易，碎片少 | 随机访问慢，链损坏影响大 |
| 索引分配 | inode 或索引块保存数据块指针 | 支持随机访问，扩展灵活 | 小文件有索引开销 |

现代类 UNIX 文件系统常使用 inode + 多级索引。

---

# 直接与间接索引

inode 常包含：

- 若干直接块指针
- 一级间接块指针
- 二级间接块指针
- 三级间接块指针

计算模板：

```text
每个索引块能放的块号数 = block_size / block_number_size

最大文件块数 =
  direct_count
  + n
  + n^2
  + n^3
```

其中 `n = block_size / block_number_size`。

---

# inode 寻址计算例题

题设：

- 块大小 512 B
- 块号 4 B
- 5 个直接块
- 1 个一级间接
- 1 个二级间接

一级间接块容量：

$$
512 / 4 = 128
$$

最大文件大小：

$$
(5 + 128 + 128^2) \times 512 = 8,456,704\ \text{B}
$$

约 `8.07 MiB`。

---

# inode 寻址读盘次数

读取 100 KB 文件第 80000 字节：

$$
80000 / 512 = 156
$$

逻辑块范围：

- 直接块：0-4
- 一级间接：5-132
- 二级间接：133 起

所以逻辑块 156 在二级间接范围。需要读：

1. 二级间接索引块
2. 对应一级间接索引块
3. 目标数据块

答案：3 次磁盘读。

---

# 空闲空间管理

文件系统要记录哪些数据块空闲。

常见方法：

| 方法 | 思路 |
|---|---|
| 位图 bitmap | 每个块用 1 bit 表示空闲/已分配 |
| 空闲链表 | 空闲块串成链表 |
| 空闲块索引 | 用索引块管理一批空闲块 |

位图优点：

- 简洁。
- 易于查找连续空闲块。

位图缺点：

- 大磁盘上扫描可能有成本。

---

# 块缓存 Block Cache

块缓存的作用：

- 减少重复读磁盘。
- 合并和延迟写入。
- 统一管理文件系统块访问。
- 支持预读，提高顺序访问性能。

风险：

- 延迟写提高性能，但崩溃时脏块可能尚未落盘。
- 这会带来一致性问题，需要日志或 fsck 等机制处理。

判断题：

| 说法 | 判断 |
|---|:---:|
| 块缓存可以减少重复读磁盘，也可能因延迟写导致崩溃时脏块尚未落盘。 | <span class="ok">√</span> |

---

# 块缓存例题

100 KB 文件，块大小 512 B：

$$
\lceil 102400 / 512 \rceil = 200
$$

第一遍顺序读：

- 200 个数据块
- 1 个一级间接索引块
- 二级间接部分需要 1 个二级间接块 + 1 个一级间接块

约 `203` 次读盘。

第二遍：

- 大部分块在缓存中。
- 理想情况下磁盘 I/O 接近 0。

---

# 页缓存与虚拟内存

页缓存 Page Cache：

- 统一缓存文件数据块和内存页。
- 文件数据可映射到进程虚拟地址空间。
- 文件读写可转换成对内存页的访问。
- 可能触发缺页异常。
- 写入后页变脏，稍后回写磁盘。

关系：

```text
文件数据块 <-> 页缓存页 <-> 进程虚拟地址空间
```

重点：

> 页面置换需要协调匿名页、文件页、页缓存占用的内存。

---

# read 系统调用到磁盘

```text
用户态 read(fd, buf, len)
  -> ecall/trap
  -> sys_read
  -> 当前进程 fd 表
  -> file 对象
  -> inode + 当前 offset
  -> 计算逻辑块号
  -> 查块缓存
  -> 缓存未命中则发起块设备 I/O
  -> virtio / DMA / 中断完成
  -> 数据进入块缓存
  -> copy_to_user 到用户 buf
  -> 更新 file offset
```

---

# 用户缓冲区与虚拟内存

`read(fd, buf, len)` 中的 `buf` 是用户虚拟地址。

内核不能直接写：

- 地址可能无效。
- 权限可能不允许写。
- 缓冲区可能跨页。
- 可能指向恶意地址。

内核必须：

- 根据当前进程页表翻译用户地址。
- 检查用户态可写权限。
- 用 `copy_to_user` 类机制写入。

文件系统与虚拟内存的交点就在这里。

---

# 文件系统与进程

进程相关结构：

```text
Process
  -> fd table
      fd -> file object
             -> inode / pipe / device
```

关系：

- 每个进程有自己的 fd 表。
- `fork` 后子进程继承 fd 表。
- `dup` 和 `fork` 可能让多个 fd 指向同一 file 对象。
- file 对象引用计数决定何时释放。
- 进程退出时，内核关闭其 fd 表中仍打开的 fd。

---

# 文件系统与线程

同一进程内线程通常共享：

- 地址空间
- 打开文件表
- file 对象引用

因此：

- 多线程对同一 fd 读写通常共享 offset。
- 多线程并发文件访问需要同步。
- 对共享文件对象加锁时，要明确锁关联到 PID、file 还是 inode。

重点：

> 同一进程内线程共享打开文件表，但每个线程仍有自己的执行上下文。

---

# 文件锁

文件锁用于协调多进程或多线程访问文件。

| 类型 | 含义 |
|---|---|
| 共享锁 LOCK_SH | 多个读者可兼容 |
| 排他锁 LOCK_EX | 与任何其他锁冲突 |
| 咨询锁 | 只有调用锁接口的程序自觉遵守 |
| 强制锁 | 普通 `read/write` 也要检查锁 |

设计关键：

- 锁关联到 `struct file`、inode 还是 PID？
- fork / dup / open / close 后锁如何继承或释放？
- 阻塞等待时不能持有文件系统内部锁睡眠。

---

# struct file 关联锁的语义

若锁关联到 `struct file`：

- `fork` 后父子共享同一个 file，也共享这把锁。
- 子进程通过继承 fd 访问同一 file，不应被自己的锁阻塞。
- `dup` 后多个 fd 指向同一 file，也共享锁身份。
- 最后一个 close 释放 file 时释放锁。

若强制锁要影响重新 `open` 的其他进程：

- inode 上仍需维护全局锁状态。
- file 用于判断“是否自己持有的锁”。

---

# 崩溃一致性问题

文件系统更新通常要改多个磁盘结构。例如追加一个数据块可能要写：

- 数据块 Db
- inode
- 数据位图 bitmap

问题：

> 磁盘写入不是天然原子操作。如果只写了一部分就崩溃，文件系统可能进入不一致状态。

可能后果：

- 空间泄露
- inode 指向垃圾数据
- 位图和 inode 不一致
- 已分配块无人引用

---

# fsck

fsck 的思路：

- 允许不一致发生。
- 重启后扫描文件系统。
- 修复元数据内部一致性。

检查内容：

- superblock 是否合理
- 位图与 inode 是否一致
- inode 类型和状态是否合法
- 链接计数是否正确
- 是否存在重复块指针
- 是否存在坏块指针
- 目录项格式和 `.`、`..` 是否正确

不足：

- 大磁盘扫描很慢。
- 可能丢失用户数据。

---

# 日志文件系统

日志 Journaling，又称预写日志 Write-Ahead Logging。

核心思想：

> 在覆写真正的文件系统结构之前，先把“将要做什么”写到日志区域。

好处：

- 崩溃后不用扫描整个磁盘。
- 只需检查已提交日志。
- 对已提交但未 checkpoint 的事务 redo。

日志用运行时额外写入，换取崩溃恢复速度和一致性。

---

# 日志事务流程

典型数据日志流程：

1. Journal write  
   把事务开始块、元数据、数据写入日志。
2. Journal commit  
   写入提交块，等待完成。事务被认为 committed。
3. Checkpoint  
   将事务内容写到最终磁盘位置。
4. Free  
   日志空间可回收复用。

崩溃恢复：

- commit 前崩溃：丢弃未完成日志。
- commit 后、checkpoint 前崩溃：重放日志。
- checkpoint 后崩溃：已经完成。

---

# 元数据日志

数据日志记录数据和元数据，可靠但慢。

元数据日志只记录元数据，常见优化：

```text
Data write
  -> Journal metadata write
  -> Journal commit
  -> Checkpoint metadata
  -> Free
```

关键顺序：

> 先把数据块写到最终位置，再提交指向该数据块的元数据日志。

这样可以避免 inode 指针指向尚未写入的新数据块，导致读到垃圾数据。

---

# 日志模式比较

| 模式 | 记录内容 | 数据写入顺序 | 特点 |
|---|---|---|---|
| Journal mode | 数据 + 元数据 | 都写日志 | 最安全，最慢 |
| Ordered mode | 只记元数据 | 数据先于元数据提交 | 折中，常用 |
| Writeback mode | 只记元数据 | 不保证数据先写 | 快，但可能暴露旧数据或垃圾数据 |

重点：

> 日志文件系统改善崩溃后的元数据一致性恢复，但不能替代备份，也不能保证用户数据永远不丢失。

---

# 文件系统与虚拟内存

两条重要连接：

1. 文件映射到地址空间

```text
mmap(file)
  -> 进程虚拟页
  -> page cache
  -> 文件数据块
```

2. 用户缓冲区是虚拟地址

```text
read/write
  -> 内核翻译用户 buffer
  -> copy_to_user / copy_from_user
```

缺页异常可能用于：

- 文件页按需加载。
- mmap 文件访问。
- 页缓存缺失时从磁盘读入。

---

# 文件系统与块设备

文件系统不直接操作“文件内容字符串”，而是组织块设备上的块。

```text
inode 逻辑块号
  -> 文件系统块号
  -> 块缓存
  -> 块设备请求
  -> DMA
  -> 中断完成
```

设备 I/O 期间：

- 发起 I/O 的进程可能阻塞。
- 块设备完成后触发中断。
- 驱动唤醒等待该 I/O 的进程。

---

# 高频判断题汇总

| 说法 | 判断 | 解释 |
|---|:---:|---|
| inode 里直接保存文件名，所以重命名要修改 inode。 | <span class="bad">×</span> | 文件名在目录项中。 |
| 两个进程分别 open 同一文件后，读写偏移量独立。 | <span class="ok">√</span> | 分别 open 得到不同 file 对象。 |
| 硬链接和软链接都可跨文件系统。 | <span class="bad">×</span> | 硬链接通常不能跨文件系统。 |
| inode 链接计数为 0 且无打开引用后，inode 和数据块才回收。 | <span class="ok">√</span> | 目录引用和打开引用都要考虑。 |

---

# 高频判断题汇总

| 说法 | 判断 | 解释 |
|---|:---:|---|
| 软链接目标删除后，软链接本身自动删除。 | <span class="bad">×</span> | 软链接会变成悬空链接。 |
| 目录维护文件名到 inode 号的映射。 | <span class="ok">√</span> | 目录项核心功能。 |
| fd 表项直接保存所有磁盘块号，read 不需要 file 或 inode。 | <span class="bad">×</span> | fd -> file -> inode -> block。 |
| 块缓存减少重复读，也可能因延迟写丢脏块。 | <span class="ok">√</span> | 性能和一致性权衡。 |
| 日志文件系统不能替代备份。 | <span class="ok">√</span> | 日志主要解决崩溃一致性。 |
| unlink 后仍被打开的文件可能延迟释放。 | <span class="ok">√</span> | 最后 close 后才释放。 |

---

# 选择题：inode 最大文件

解题模板：

1. 先算每个索引块能放多少块号：

$$
n = block\_size / block\_number\_size
$$

2. 直接块容量：

$$
direct\_count \times block\_size
$$

3. 一级、二级、三级间接容量：

$$
n \times block\_size,\quad n^2 \times block\_size,\quad n^3 \times block\_size
$$

4. 相加。

---

# 选择题：read 路径

题干常见形式：

> 某进程执行 `read(fd, buf, len)` 读取普通文件。内核通过 fd 找到打开文件对象后，下一步最合理的是？

正确答案通常是：

> 根据 file 对象中的 inode 和当前偏移定位要读的文件数据块。

错误选项常见陷阱：

- 把 fd 当磁盘块号。
- 跳过文件系统结构扫描整个磁盘。
- read 前先关闭 fd。

# 总结：文件系统实现

- 文件系统把用户看到的字节序列组织成磁盘上的块和元数据。
- VFS 提供统一接口，具体文件系统解释磁盘布局。
- inode 保存元数据和块指针，目录项保存名字到 inode 的映射。
- fd 是进程 fd 表索引，打开文件对象保存 offset、flags 和 inode 引用。
- 文件分配方式包括连续、链式、索引；inode 多级索引支持大文件。
- 块缓存和页缓存减少 I/O，但延迟写带来崩溃一致性问题。

---

# 总结：关系

## 与进程

- 每个进程有 fd 表；fork 继承 fd；close 管引用计数。
- 进程阻塞等待磁盘 I/O，I/O 完成后由中断唤醒。

## 与虚拟内存

- 用户缓冲区是虚拟地址，内核必须查页表安全拷贝。
- mmap 可把文件页映射到进程地址空间。
- 页缓存统一文件数据块和内存页。

## 与一致性

- fsck 扫描修复，慢且可能丢数据。
- 日志通过预写日志和重放改善崩溃恢复。
